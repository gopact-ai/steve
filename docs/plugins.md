# Steve 插件系统规划

状态：已实现包准备、节点部署协议、配置与凭据版本、内容复制，以及会话隔离运行目录、固定 MCP broker、运行引用持久化和管理服务/API 的导入、配置、准备查询。管理页面、预设实例化/迁移、安全移除和完整 P5 验收尚待完成。下文是第一轮终态；[本地包准备](plugins-local.md) 记录已可使用的命令。

## 目标与第一轮边界

用户安装一个能力包，就能获得完成某类工作的工具、技能和 Agent 预设，并知道它在哪些机器上可用、哪些项目可以使用、哪些会话仍在使用旧版本。作者维护自己的包，新增业务集成无需修改 Steve 核心。

第一轮交付 **Skills + MCP 声明 + Agent 预设** 的统一安装、配置、启用、版本固定、节点分发与安全卸载。Agent 预设引用机器已有的 harness；工作流模板、验证器、外部触发器、通用 hooks 和新的 harness 安装适配属于后续轮次。channel 可以沿用相同的包身份和管理规则，其运行契约另行设计。

本轮以两个真实用途验收：GitHub 协作包、团队内部工具包。两者都通过现有任务入口手动使用；Issue 自动派单和 CI 自动诊断是第二轮能力，第一轮不承诺。

100 行棘轮是独立维护任务，不作为插件规划的前置条件；实现继续遵守当前 120 行阈值与空基线。

## 已有基础与实际缺口

| 能力 | 当前落点 | 需要新增的边界 |
|---|---|---|
| 技能来源、确定性打包和节点分发 | `internal/skills`、`internal/node/skills.go` | 多能力包身份、版本与作用范围；按会话固定的技能视图 |
| MCP 发现、安装与节点绑定 | `internal/mcpregistry`、`internal/admin/admin_mcp.go`、`internal/node/mcpbroker.go` | 包内服务命名、精确版本与节点安装回执；版本化的服务定义 |
| Agent 配置与原子目录发布 | `internal/agent`、`internal/admin` | 包预设的来源、用户覆盖及升级冲突；预设不自动覆盖用户配置 |
| 会话能力指纹与漂移检查 | `internal/capability`、`internal/turn` | 固定包摘要、运行目录与 MCP 定义，并在重启后恢复引用 |
| 节点能力与执行准入 | `internal/ability`、`internal/roster`、`internal/node` | 协商插件协议，报告节点实际准备的版本；准入核验目标精确版本 |
| 持久命令、配置提交和恢复 | `internal/ledger`、`internal/config`、`internal/app` | 安装/激活/卸载管理操作的回执、CAS 与配置投影恢复 |

尤其需要改变现有 Skills 更新路径：`skills.Live.applyLocked` 会重新物化共享 harness 技能目录，并调用重启回调。增加版本号和指纹不能阻止旧进程在运行中读到被替换的技能。第一轮必须建立不可变的运行配置与目录，再允许新旧版本同时使用。

现有 MCP/Skills 配置也不会因为包装成插件就获得额外的进程沙箱、网络限制或副作用代理。第一轮保持可信作者、显式安装的执行模型，界面如实列出命令、外部服务和凭据用途。

## 一个包可以贡献多个扩展点

包是安装与升级单位，扩展点是核心调用它的契约。包内运行代码优先复用已有协议：工具通过 MCP，Agent 通过 ACP，技能与预设通过声明。运行代码使用受管理的外部进程或服务；第一轮不引入 Go 动态库、反射式注册框架或第三种 Agent 执行协议。

| 扩展点 | 第一轮 | 后续方向 |
|---|---|---|
| Skills | 包内技能及其资源，按授权范围装配 | 工作流模板与团队能力包 |
| MCP | 固定服务定义、安装来源、参数与配置需求 | 更多现有安装方式的适配 |
| Agent 预设 | 现有 harness、模型偏好、技能/MCP 组合 | 预设与工作流协作 |
| Harness | 复用已有接入和可信安装目录 | 发现、安装及 ACP 适配声明 |
| 验证器 | 复用现有验证行为 | 测试、扫描、基准和 Agent 评审的统一契约 |
| 触发器、事件处理 | 本轮不注册处理器 | Webhook、提交后事件订阅，再设计可阻断检查 |
| 知识来源、能力探测 | 本轮可作为普通 MCP 工具使用 | 显式的材料来源与节点观测契约 |
| 规划策略、报告展示 | 本轮不开放自定义运行入口 | 返回标准计划、结构化报告及专用视图 |

## 包、配置与授权

包清单 schema 1 / `steve.plugins.v1`、本地准备回执、`plugin_packages.v1` 节点准备协议与版本化凭据引用已实现，见 [本地契约](plugins-local.md)。`config.Plugins` 和共享配置保存期望安装；运行引用已进入 attempt、聊天会话和节点会话，节点通过 `plugin_runtimes.v1` 协商。

### 不可变包与可变安装

| 对象 | 必须表达的内容 |
|---|---|
| 包清单 | 作者命名空间下的稳定 ID、版本、清单 schema、Steve/节点兼容要求、能力声明、平台需求、配置项与所需权限 |
| 已解析包 | 完整源码提交或归档来源、规范化内容摘要、各能力入口、执行依赖的精确版本与可校验内容身份 |
| 安装配置 | 选择的包摘要、目标机器、启用范围、普通配置、节点凭据引用、配置修订号 |
| 节点回执 | 包摘要、配置修订号、实际准备状态、缺失依赖、失败原因、运行配置摘要 |
| 会话绑定 | 解析后的全部包与能力摘要、运行配置身份、MCP 定义版本、授权关联和持久引用 |

人可读的版本号不代替内容摘要。同一发布身份出现不同内容时拒绝覆盖并报告冲突；检查更新可以显示新版本，安装与会话解析使用固定身份。远程 MCP 的配置可以固定，其服务端实现可能独立变化，不能宣称远程服务代码也被固定或可离线重现。

第一版来源为本地目录快照和固定 Git 提交：安装时读成不可变包，本地文件或分支后续变化不影响已装版本。不做插件市场、自动更新或插件之间的递归依赖求解。可执行依赖只支持第一批样例实际需要、能够锁定版本并核验来源的方式；未支持的安装方式明确拒绝。

### 配置权威与命名

协调配置保存期望安装与启用范围，遵循现有配置文件 CAS 与持久化规则；账本保存管理操作及受理/执行回执，节点保存本机内容、运行配置和安装事实。配置投影未完成时，受影响能力停止新的准入并显示待协调状态，不把部分完成报成成功。复用现有配置恢复模式，不要求配置文件、账本和远端磁盘跨存储原子提交。

包内能力具有稳定命名空间，例如逻辑身份由“包 ID + 能力种类 + 包内名称”组成；映射到各 harness 的文件名和 MCP 名称须确定且无碰撞。与内置能力、用户同名资源的冲突必须在预览阶段指出，不能依靠装配顺序覆盖。

Agent 预设在用户选定机器与本地 Agent ID 后实例化，保存来源摘要和用户覆盖。包升级只更新模板候选；更新已有 Agent 必须呈现具体配置差异并走原有保存路径。卸载不能删除用户手写或已转为用户管理的资源。

### 作用范围与凭据

第一版以项目为使用范围、以节点为安装位置；Agent 预设本身不扩大项目权限。读取元数据、下载准备、配置凭据、启用到项目和实际执行是不同动作。安装完成不自动把工具暴露给所有 Agent，也不自动运行包内命令。

凭据声明只包含用途与配置需求；值留在执行节点或其 broker，协调元数据、包内容、同步包和日志中保存引用或脱敏状态。对远程 MCP，同样在执行节点解析连接凭据。包 ID 或包作者身份都不等于 owner 权限。

启用所需授权必须与包摘要和作用范围关联；升级增加能力、改变执行命令或凭据用途时，先展示差异再激活。权限被撤销后，旧版本绑定不恢复已经失效的授权；核心继续对它管理的调用检查执行身份和当前策略。已发出的外部请求不因停用而自动撤回。

包本身可能包含私有文档与业务逻辑，分发也遵守来源和数据等级约束；节点可联网或能执行某个二进制不代表它有权接收该包或项目内容。

## 多节点准备与激活

一次安装具有稳定管理命令 ID。相同 ID 和相同内容重试读取原操作，内容不同返回冲突。安装管理不虚构模型 attempt 或 token 消耗。

1. **预览**：解析清单和固定来源，展示能力、命令、配置需求、范围与变更；未知能力或不兼容 schema 直接拒绝。
2. **准备**：在获准机器上校验包内容、解析节点配置、准备依赖和独立运行目录。准备过程不向会话发布能力。
3. **记录回执**：节点持久记录包摘要、配置修订与实际状态；协调端核对回执身份，过期回执不能激活另一版配置。
4. **激活**：在配置与授权边界内发布完整的能力集合，再允许新会话解析。单个目标范围里的技能、MCP 与预设引用必须一致，不暴露半包。
5. **持续协调**：失败、离线和旧协议节点分别显示原因，可用同一操作重试。重启从记录恢复状态，不能把超时当成确定失败而盲目重复安装。

跨节点不承诺同时切换。期望版本统一，节点逐个准备并激活；新会话只能选择与期望摘要匹配、已准备且获准的节点。其他节点显示待同步/失败，不能静默用旧版启动新会话。已固定旧版的会话按下节保留。

包内容及部署记录应有与协调交接相匹配的恢复路径：内容进入获准的内容复制/保留机制，节点仍独立报告本机事实。共识只记录确定的描述与回执；下载、安装、进程启动和插件调用都在事务与 Raft 回放之外执行。相应管理动作沿用现有协调身份和栅栏，旧协调者的迟到请求不能激活新配置。

## 会话版本固定、升级与卸载

每个新会话解析一次已启用能力集合，得到运行配置身份。身份覆盖包摘要、技能内容、普通配置、凭据引用修订、MCP 定义和会影响启动的 harness 配置；授权关联另行检查，不能仅靠摘要授权。

物化目录和进程路由都必须使用该运行配置，不能只修改指纹。包目录不可原地替换，技能视图不指向可变源码；复用进程不得跨不兼容运行配置。需要共享同一个 ACP 进程的会话只能共享它实际支持的相同配置。P3 必须验证 hub 与节点两条启动路径。

| 动作 | 新会话 | 已绑定的会话与待恢复执行 |
|---|---|---|
| 安装但未启用 | 不可选 | 无变化 |
| 激活新版 | 解析新版及其配置 | 继续使用原摘要、目录与服务定义 |
| 回退默认版本 | 经兼容与授权检查后解析选定旧版 | 各自保留原绑定，不回滚任务与外部副作用 |
| 停用 | 阻止新的会话绑定 | 显示仍在使用的会话；在现有授权下完成或由用户显式停止 |
| 移除内容 | 无入口 | 所有持久引用释放并确认没有相关进程后才回收 |

存活但空闲的会话仍是引用；失联节点、停止未确认或可恢复执行也不能按超时清零。卸载先停止新绑定，再展示阻塞项；不因卸载强杀 Agent。需要紧急撤权时走现有撤权/停止路径，并保留未确认的对账状态。

重启或协调交接后，从会话、待恢复执行与节点记录重建引用，不能只靠进程内引用计数。原版本丢失时明确进入待恢复状态，不用当前最新版替代，更不能为补装而重放已发送的 prompt。

这一目标要求扩展当前共享技能目录、harness 进程复用、MCP 绑定与会话记录。P3 未通过前，P1/P2 只能提供预览和准备；不能提前开放会影响会话的激活、升级或卸载。

## 核心职责与后续事件契约

`ledger`、`attempt`、`task`、`lifecycle`、`execution`、`artifact` 和 `coordination` 继续掌握事务提交、预算、租约、执行停止、恢复与落地。插件使用核心提供的窄接口，不能取得数据库事务或任意推进任务状态。内部生命周期函数的钩子也不直接公开为插件 API。

第二轮先开放提交后事件订阅：事件与提交事实关联，处理器在提交后运行，有稳定事件/投递身份与可恢复回执。重试按至少一次投递设计；外部目标不支持幂等时，对结果不明的调用提供对账，不能承诺恰好一次。

可阻断检查单独设计在准入/验证边界，并规定顺序、期限、失败处理和结果生效条件；外部调用结束后仍要复核受检修订及执行授权。已经发生的落地与对外操作不能被一个迟到的 block 撤销。Steve 能观察和控制的是它承载的入口，不能把 harness 内部所有工具调用都算作已被统一拦截。

## 第一轮实施与验收

以下按依赖顺序推进，每一步一个可独立复核的 PR。这里的编号属于插件规划，不续用重构文档的 M0–M6。

| 阶段 | 交付 | 验收 |
|---|---|---|
| **P0：契约与两个样例** | 固定清单 schema、配置与授权模型、能力命名、兼容协商、包摘要规则、管理操作及会话引用字段；准备两个能力包样例 | 样例无需给核心增加业务专用字段；语法/身份/版本/配置错误有明确拒绝；逐项说明现有入口如何接入 |
| **P1：本地不可变安装** | 本地目录与固定 Git 提交导入、预览、摘要校验、安装记录、独立暂存和可恢复准备 | 源目录变化不改已安装包；中断重试不混入旧文件；路径逃逸、摘要不符与同发布身份内容冲突被拒绝；不激活或自动启动 |
| **P2：节点准备与协调恢复** | 协议协商、节点配置/凭据引用、包分发、精确版本回执、跨节点状态与管理操作恢复 | 离线/旧节点/缺凭据/缺运行时分别可解释；回执丢失可重查；过期协调身份或配置修订不能发布；交接后可继续协调 |
| **P3：会话绑定与生命周期** | Skills/MCP/Agent 预设装配、不可变运行配置、进程复用隔离、持久版本引用、激活/升级/停用/回收 | v1 会话跨 v2 激活与协调重启仍读到 v1；新会话用 v2；多个项目不会串配置；不重启无关 harness；停止未确认时不回收引用 |
| **P4：统一管理与迁移** | 管理服务/API/页面；安装预览、目标机器、范围、缺失配置、版本、受影响会话、升级/回退/移除 | 用户可完成完整管理流程；操作幂等并可重查；用户配置不被覆盖；已有 Skills/MCP/Agent 配置继续工作，显式采用为插件资源时不重复装配 |
| **P5：样例与故障验收** | 两个样例端到端跑通、作者指南、运维/恢复说明与验证记录 | 完成下列场景；所有支持行为可从 UI 和持久记录解释；代码、文档及协议一致 |

P0 要同时定义旧配置与新插件资源的唯一归属，P4 再开放迁移入口；不能出现 Skills 页更新一个定义、插件页又维护另一份同名定义的双重权威。插件拥有的内容在旧资源页应显示来源并引导到对应管理入口；用户原有资源仍按原方式管理。

P5 的最小场景集：

- **GitHub 协作包**：在测试仓库中配置指定节点的凭据、启用审查技能和 MCP、从预设创建 Agent 并完成一次手动审查；另一个无授权项目看不到这些能力。
- **团队工具包**：复用同一清单表达内网工具、团队规范和 Agent 预设；只能在获准且满足实际运行条件的节点执行。CI 用隔离服务替身，真实服务验收单独记录。
- 两个包同时安装，无名称覆盖；至少一个场景运行在远端节点，hub 不保存节点密钥。
- 下载/准备中断、依赖缺失、错误摘要、安装回执丢失、配置提交后投影未完成，各自能恢复或明确拒绝。
- 新旧版本并存、用户预设覆盖冲突、旧版被会话引用时移除、节点离线和停止未确认时回收，均符合版本表。
- 协调切换前已接受的工作继续使用原版本，不重复 prompt、不新增预算扣费、不把结果不明报告为成功。

验证按实际改动范围执行包测试、竞态与架构门禁；发布前跑完整后端测试。涉及 UI 时执行控制台门禁；涉及执行、节点或落地路径时按 [CONTRIBUTING.md](../CONTRIBUTING.md) 提供真机门禁证据。本地准备命令只操作显式指定的包存储，不涉及线上执行。

## 后续轮次与交接

第一轮闭环后再规划：

1. **验证器与自动化**：标准验证结果、外部触发受理身份、提交后事件投递；再扩展可阻断检查。使用 GitHub 包的 Issue/CI 场景验证。
2. **接入与领域扩展**：harness 发现/安装适配、知识来源、节点能力探测、规划策略和结构化报告。每种协议由真实第二个实现验证后再稳定。
3. 任意前端代码、插件市场、递归依赖求解、热替换核心状态机和多租户不可信代码执行不在当前路线的承诺内。

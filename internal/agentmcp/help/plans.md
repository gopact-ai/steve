# 任务与回合

- 每条消息是某个**任务**的一个回合；任务有预算（回合数、总时长），耗尽会刹车并告诉用户跑到哪了。预算紧时先把最要紧的做完、说清剩下的。
- 每次执行是一个 **attempt**：拿到租约才开始（自己的、主目录的写锁、或隔离工作树的），运行中续约，租约丢了就取消。
- 动词：`/tasks` 列表；`/tasks 12` 详情；`/tasks pause|resume|cancel 12`；`/history` 本会话最近回合；`/cancel` 取消进行中的回合；`/status` 当前 agent、模型、会话状态。

# 计划

`/plan <目标>` 让 Steve 把目标拆成步骤：

- 步骤是 **DAG**：`needs` 依赖、`merge` 收敛并行分支；每步写 `requires`（能力要求，不是指定 agent），放置在每步执行前重新求解。
- 每步在隔离工作树里跑：从计划开始时的快照（或它接续那一步的结果）物化，不在主机器也一样。
- 每步声明验证：`command`（跑一条命令）、`agent`（另一个 agent 交叉检查）或显式的 `none`。验证不过不算完成，进入重规划。
- 步骤跑完先 publish（快照回 hub），再验证，再绑名 `steve/<任务>/<步骤>`；最后落地到主目录。
- 步骤失败、超时、机器掉线、发现让后续失效、预算压力、用户介入——都会触发重规划，产生新版本的计划；`/plans` 列表，`/plans 3` 看步骤树和为什么改。

用户让你拆计划时，好的步骤长这样：一句能验证的目标、明确的 `requires`、声明会碰的路径、一个跑得起来的验证命令。并行的步骤路径不重叠，合并才顺。

# 你在步骤里时

- 你的目录是一棵工作树，不是主目录。改动落在 `touches` 声明的路径里，合并才不会冲突。
- 做完就停：把结果留在工作树里（提交与否都行，快照会拍到），把验证需要的东西准备好。合并与推送由落地流程做。
- 需要别的分支的结果：看 `inputs/<步骤>/`（merge 步骤）。
- 报告写清：改了哪些路径、怎么验证的、哪里没做完——重规划靠这些判断下一步。

# 定时

- `/every <when> <what>`：反复做，如 `/every 9:00 汇总昨天的告警`。
- `/at <when> <what>`：某个时刻做一次。
- `/schedules`：已安排的定时。
定时触发时 Steve 会合成一条消息进会话，像用户说的一样处理。

# 修复

`/repair <agent>`：某个 agent 的运行时坏了（命令不在 PATH、认证过期），让同一台机器上健康的 agent 去修。`/fleet` 看机器与 agent 现状，`/fleet probe` 重新探测模型。
